## Layer Responsibilities

### 1. `core/`
Things used throughout the application.

```
core/
├── constants/
│   └── app_constants.dart
├── theme/
│   └── app_theme.dart
└── utils/
    ├── app_utils.dart
    └── duration_utils.dart
```

- **`constants/`** (`app_constants.dart`): App-wide constant values, strings, dimensions, and keys.
- **`theme/`** (`app_theme.dart`): Centralized Material 3 `ThemeData` definitions (`lightTheme`, `darkTheme`, color schemes).
- **`utils/`** (`duration_utils.dart`, `app_utils.dart`): Helper functions and formatters used throughout the app.

### 2. `models/`
Data structures used by the application.

```
models/
├── album.dart
├── artist.dart
├── audio_metadata.dart
├── folder_node.dart
├── genre.dart
├── search_results.dart
└── track.dart
```

#### `Track` Model Fields:
- `id` (`String`): Unique track identifier.
- `title` (`String`): Title of the track.
- `artist` (`String`): Artist name.
- `album` (`String?`): Album name.
- `albumArtist` (`String?`): Album artist name.
- `genre` (`String?`): Musical genre.
- `year` (`int?`): Release year.
- `trackNumber` (`int?`): Track index within album.
- `discNumber` (`int?`): Disc number.
- `duration` (`Duration`): Duration of the track.
- `filePath` (`String`): Local path or URI to the audio file.
- `fileName` (`String?`): Basename of the file.
- `fileSize` (`int?`): File size in bytes.
- `mimeType` (`String?`): Audio MIME type.
- `isAsset` (`bool`): Whether bundled as asset.
- `albumArtUri` (`String?`): Extracted or MediaStore artwork URI.

All models support `copyWith`, `toMap`, `fromMap`, `toString`, and equality operators.

### 3. `services/`
Underlying application functionality and platform interfaces.

```
services/
├── audio/       # Playback engine facade (AudioPlayerService) — bridges to MusicAudioHandler
├── permissions/ # Android/iOS runtime permissions (AudioPermissionService)
├── scanner/     # Local device storage & MediaStore scanning (MusicScannerService)
├── metadata/    # ID3 tag extraction and audio metadata parsing
├── artwork/     # Cover art extraction, memory & disk caching
├── playback/    # Persistent playback data (PlayHistoryService, Phase 3H)
└── playlists/   # Persistent user playlists (PlaylistService, Phase 3J)
```

#### Phase 2A — MediaStore Scanner Service Abstraction:
- **`MusicScannerService`**: Provides an architectural abstraction wrapping `OnAudioQuery` and Android MediaStore.
- **Decoupling Rule:** The UI and application code never interact directly with `OnAudioQuery` or platform-specific permission constants; they interact solely with `MusicScannerService`.
- **Target Permissions (Android):**
  - Android 13+ (API 33+): `android.permission.READ_MEDIA_AUDIO`
  - Android 12 and below (API $\le$ 32): `android.permission.READ_EXTERNAL_STORAGE`
  - Unnecessary permissions (`READ_MEDIA_IMAGES`, `READ_MEDIA_VIDEO`, `WRITE_EXTERNAL_STORAGE`, `MANAGE_EXTERNAL_STORAGE`) are omitted.

### 4. `database/` & `data/repositories/`
Local SQLite persistence via Drift.

```
database/
├── app_database.dart   # AppDatabase: tracks/artists/albums/genres/play_history/favorites/playlists (schema v7)
├── track_repository.dart
└── tables/
    ├── play_history.dart
    ├── favorites.dart
    ├── playlists.dart
    └── playlist_tracks.dart
data/repositories/
└── music_repository.dart
```

#### Relational Schema Tables:
- `tracks`: Track metadata, file paths, durations, foreign keys.
- `artists`: Normalized artist entities.
- `albums`: Normalized albums with artist links and artwork.
- `genres`: Normalized genres.
- `play_history`: Denormalized play history (Phase 3H) — per-track `playCount`, `lastPlayedAt`, `resumePositionMs` with the full track snapshot denormalized (trackId PK). Migrations added at schema v5.
- `favorites`: Denormalized user favorites (Phase 3I) — trackId PK with the full track snapshot + `favoritedAt`; a track can be favorited at most once (toggle removes). Migrations added at schema v6.
- `playlists`: User-created playlists (Phase 3J) — `id` (UUID v4), `name`, `created_at`.
- `playlist_tracks`: M2M playlist membership (Phase 3J) — `playlist_id` FK → playlists `ON DELETE CASCADE`, `track_id`, `position`; composite PK `(playlist_id, track_id)` so a song belongs to a playlist at most once. Migrations added at schema v7.
- `playlist_history`: Per-playlist playback history (Phase 3K) — `playlist_id` PK (the playlist UUID; no FK), `play_count`, `last_played_at`. Separate from per-song `play_history`; only explicit playlist-level plays count. Migrations added at schema v8.

#### Phase 2N — High-Performance SQLite Search Engine:
- Searches are executed directly in SQLite via parameterized `LIKE` queries with joins and limits inside `DriftMusicRepository`.
- **Avoid Manual In-Memory Filtering:** Large libraries are queried directly in the database rather than loading entire libraries into Dart memory.
- **Search Scope:**
  - **Songs:** `title`, `artist`, `album`, `fileName`
  - **Artists:** `name`
  - **Albums:** `title`, `artist`
  - **Genres:** `name`
  - **Folders:** `filePath` directory segments
  - **Playlists:** `name` — matched **client-side** in `SearchControllerNotifier._matchingPlaylists(query)` over the live `PlaylistService` data (spec 16: "reuse the same underlying playlist data", no separate index); shipped with the SQLite media results in `SearchResults.playlists`.

#### Album/artist drilldown — MediaStore ids, not names (blank album + artists screens):
- **`tracks` carries BOTH a name and a MediaStore id** for each level (`artist` + `artist_id`, `album` + `album_id`, `genre`), and every level of the library hierarchy is keyed by the **id**: `Album.id` is an `int` MediaStore `albumId` (built by `AlbumRepository.synchronizeAlbums`/`DriftMusicRepository.getAlbums`), `Artist.id` is the `artistId` as a string (`ArtistRepository._mapEntry`). A detail screen therefore **must look up by id** — filtering the `album`/`artist` *name* column against an id matches nothing and renders an empty screen.
- `saveTracks` persists `artistId` **and** `albumId`. Omitting `artistId` here silently emptied the normalized `artists` table: `synchronizeArtists` skips tracks with a null id, so the Artists page had zero rows and every artist count (`ArtistRepository.getTrackCount`, which counts on `tracks.artist_id`) read 0 — while Albums still worked, because `albumId` was persisted.
- `DriftMusicRepository` exposes id-keyed lookups: `watchTracksByAlbumId`/`getTracksByAlbumId(int albumId)` (matches the `album_id` column, ordered disc → track → title) and `watchTracksByArtistId`/`getTracksByArtistId(int artistId)` (already present). The `watchTracksByAlbum(String)` / `watchTracksByArtist(String)` **name** variants match the title/name column and are kept for name-keyed callers only — they cannot resolve an id. `albumTracksProvider` (name) and `albumTracksByIdProvider` (int) mirror that split; **`AlbumDetailScreen` uses `albumTracksByIdProvider`**, falling back to the title lookup only when `album.id == 0` (tracks grouped without a MediaStore id).
- Rule of thumb: an `Album`/`Artist` object carries its id in `.id`, so the `*ById` provider is the correct one; reach for the name variant only when you genuinely hold a name.

#### Phase 3H — Playback History Service (Drift-backed):
- **`PlayHistoryService`** (`lib/services/playback/play_history_service.dart`) persists recent plays in the `play_history` table, de-duplicated by track id. Public surface: `record(Track)` (moves a replay to the top and increments `playCount`; the persisted `lastPlayedAt` is bumped to the replay time so the DB ordering matches the in-memory reorder across restarts), `saveResumePosition(trackId, position)`, `removeEntry(trackId)`, `clear()`, `dispose()`, `hasBackingStore`, `getRecentlyPlayed({limit})` + `watchRecentlyPlayed({limit})` (3H.11 — bounded `ORDER BY last_played_at DESC LIMIT ?` read the `recentlyPlayedProvider` runs on), `getRecentlyPlayedTracks({limit})` (3H.30 — the most-recent `Track`s, available only), and `pruneMissingTracks(availableTrackIds)` (3H.29 — lazy removal of history whose music file was deleted, called when the Recently-Played/History UI is shown, never touching the song/track itself); exposes live `entriesStream` + snapshot `entries`, each as an immutable `PlayHistoryEntry{track, playedAt, playCount, resumePosition}`.
- Providers: `playHistoryServiceProvider` (backed by `appDatabaseProvider`) and `recentlyPlayedProvider` (`StreamProvider` of entries, most recent first for the Library/History UI). Constructor is `PlayHistoryService([db, maxEntries = 50])`; the no-arg form is used by test stubs (`NoopPlayHistoryService` overrides `record`).
- Library's "Recently Played" row tiles expose a per-entry remove (`removeEntry`); the full `HistoryScreen` (`lib/screens/library/history_screen.dart`) lists all history with play counts + a clear-all action.

#### Phase 3I — Favorites Service (Drift-backed):
- **`FavoritesService`** (`lib/services/favorites/favorites_service.dart`) persists user favorites in the new `favorites` table (schema v6 migration; `trackId` PK with a full denormalized Track snapshot + `favoritedAt`; a track can be favorited at most once — a toggle removes). It starts restoring eagerly on construction (`_ready = _ensureLoaded()`, exposed as `ready`) so the fast **in-memory** mirror (`_favoriteIds` set + `_entries` list) is warm before first use. Public surface: `isFavorite(Track)`/`isFavoriteId(id)` + `favoriteIds` (O(1) membership lookup, no DB round-trip during UI builds), `addFavorite`/`removeFavorite`/`removeFavoriteId`/`toggleFavorite`/`clearFavorites`, `count`, `hasBackingStore`, live `entriesStream` + snapshot `entries` (each an immutable `FavoriteEntry{track, favoritedAt}`), `favoriteTracks`/`favoriteTracksAvailable`, and `pruneMissingTracks(availableTrackIds)` (3I.29 — lazy removal of favorites whose music file was deleted, called when the Favorites screen is shown, never touching the song itself). **Sorting** (3I): `FavoriteSort` enum (`newest` default / `artist` / `title`), applied in-memory by `entries`/`entriesStream`/`favoriteTracks`.
- Providers: `favoritesServiceProvider` (`Provider`, backed by `appDatabaseProvider`, disposes the service) and `favoriteIdsProvider` (`StreamProvider<Set<String>>`, awaits `service.ready` then mirrors `entriesStream` so list tiles render the filled vs. outline heart without per-track queries). Constructor is `FavoritesService([db, sort = newest])`; the no-arg form (`FavoritesService(null)`) is an in-memory test stub overridden in widget tests (`ProviderContainer.overrideWithValue(FavoritesService(null))`) so no real Drift DB is built.
- `FavoritesScreen` (`lib/screens/library/favorites_screen.dart`) lists favorited tracks (reusing `TrackTile`), offers a sort bottom sheet, per-row unfavorite (heart toggle), an empty state, and prunes deleted files on show. Favorite entry points: `TrackTile`'s heart (now a `ConsumerWidget`), `MiniPlayer`/`ConnectedMiniPlayer` heart button, `PlayerScreen`'s AppBar heart action, and the `TrackOptionsSheet` Favorite action (now wired to `toggleFavorite`, no snackbar stub). `LibraryScreen` gained a "Favorites" tile (with count) and `HomeScreen` a Favorites quick-access tile. Tests: `test/services/favorites_service_test.dart` (12, incl. Drift-backed persistence).

#### Phase 3J — Playlist Service (Drift-backed):
- **`PlaylistService`** (`lib/services/playlists/playlist_service.dart`) persists user-created playlists in two new tables (schema v7 migration): `playlists` (`id` UUID v4 — never the mutable name, 3J.5 — `name`, `created_at`) and `playlist_tracks` (`playlist_id` FK → playlists `ON DELETE CASCADE`, `track_id`, `position`, composite PK `(playlist_id, track_id)` so a song joins a playlist at most once). A single shared `_ready = _restore()` future (exposed as `ready`) eagerly restores persisted playlists on construction and is awaited by **every** mutation — a slow restore can never clobber state created before it finished. Public surface: `createPlaylist(name)` / `renamePlaylist(id, name)` / `deletePlaylist(id)` / `addTrackToPlaylist(id, track)` (idempotent, 3J.3) / `removeTrackFromPlaylist` / `moveTrack(oldIndex, newIndex)` (clamped, rewrites `position` for every row via the atomic delete-all + re-insert `_rewritePositions` transaction) / `contains` / `trackCount` / `tracksForPlaylist` / `getPlaylist` / `playlists` snapshot + live `playlistsStream` (broadcast) / `pruneMissingTracks(availableTrackIds)` (3J.1 — lazy removal of playlist entries whose music file was deleted, called when the Playlist detail screen is shown; never touches the song itself). UUIDs are generated with a `Random.secure()`-based v4 (no `uuid` package in pubspec).
- Providers: `playlistServiceProvider` (`Provider`, backed by `appDatabaseProvider`, disposes the service) and `playlistsProvider` (`StreamProvider` yielding `service.playlists` then `service.playlistsStream`). Constructor is `PlaylistService([db])`; the no-arg form (`PlaylistService(null)`) is an in-memory test stub overridden in widget tests so no real Drift DB is built.
- UI (Phase 3J): `PlaylistsScreen` (`lib/screens/library/playlists_screen.dart` — list with song counts + creation date, create/rename/delete dialogs, empty state); `PlaylistDetailScreen` (`lib/screens/library/playlist_detail_screen.dart` — live header via `playlistsProvider`, Play/Shuffle buttons feeding `PlayerNotifier`, `SliverReorderableList` drag handles → `moveTrack`, per-row Remove-from-playlist / Play-next, rename dialog, prune-on-show, empty state → `SongsListScreen`); `showAddToPlaylistSheet` (`lib/widgets/playlist_picker_sheet.dart`) — "Add to Playlist" bottom sheet (new-playlist-with-track + existing playlists with a check mark when already added), wired into `TrackOptionsSheet`'s Add to Playlist action (snackbar stub replaced); both sheet functions defer to the shared `showPlaylistPicker` (specs 18-19). **Multi-select (3J.16):** `AddSongsScreen` (`lib/screens/library/add_songs_screen.dart`) opens from the detail screen's AppBar `playlist_add` action and the spec 3J.13 empty state ("No songs yet"/"Add Songs"); it reuses the library tracks + `TrackTile` with checkboxes, pre-checks-and-locks songs already in the playlist (3J.17), and sends the selections to the playlist in selection order on "Add N Songs". `PlaylistDetailScreen`'s empty state renders the spec 3J.13 layout (name header, music-note icon, "Add songs to start building your playlist.", Add Songs button). **Home (3J.36):** `HomeScreen` gained a "Your Playlists" horizontal row of the newest-created few playlists (capped at 4, `playlistsProvider` + `trackCount`, spec 3J.38 new-created-first) with a "See all" header action → `PlaylistsScreen`; the row is hidden when no playlists exist. **Context menu (3J.37):** each playlist row's `PopupMenuButton` now offers Play / Shuffle (hidden for empty playlists) / Add Songs (`AddSongsScreen`) / Rename / Delete — with Play Next / Add to Queue added in Phase 3K. `LibraryScreen` gained a Playlists tile (with count via `playlistsProvider`) and `HomeScreen` a Playlists quick-access tile. Tests: `test/services/playlist_service_test.dart` (16, incl. Drift-backed CRUD/reorder/restart persistence) + `test/screens/playlists_screen_test.dart` (17 widget tests, incl. multi-select picker, row context menu, Home "Your Playlists" row).

#### Phase 3K — Playlist Improvements (search, sort, history, queueing):
- **Playlist Search (3K.1):** `PlaylistsScreen` now renders a persistent search `TextField` when playlists exist — a pure client-side, case-insensitive substring filter over the already-loaded `playlistsProvider` list (no DB/filesystem query, no debounce). A "no matches" empty state (`search_off` icon + `No playlists match "<query>"` + a Clear search button) replaces the list while a query matches nothing; the global "No playlists yet" empty state is untouched.
- **Playlist Sorting (3K.2):** `PlaylistSort` enum (`newest` default / `oldest` / `nameAZ` / `nameZA`) lives in `playlists_screen.dart` with a pure, unit-tested `sortedPlaylists(playlists, sort)` helper; the screen's `_applyView` filters then sorts. Sorting is UI-only — the stored playlist order (creation order) is never mutated. UI: a sort `IconButton` in the AppBar opens the favorites-style radio bottom sheet ("Sort playlists").
- **Playlist History (3K.3):** new `playlist_history` table (schema v8 migration) + `PlaylistHistoryRepository` (`lib/data/repositories/playlist_history_repository.dart`) + `playlistHistoryRepositoryProvider` (backed by `appDatabaseProvider`). #### Phase 4A — Sleep Timer Service:
- **`SleepTimerService`** (`lib/services/sleep_timer_service.dart`) is a countdown timer **independent of the audio engine** — it only tracks a remaining `Duration` and fires exactly one `expiredStream` event at zero. `start(duration)` replaces any active countdown (a zero/negative duration expires immediately), `cancel()` clears remaining + deactivates **without touching playback/history/queue/playlists**, and ticks run on a plain Dart `Timer.periodic` (`tickInterval` injectable, default 1s) so the countdown keeps working in background/lock-screen while the audio foreground service keeps the isolate alive (spec §7). The remaining time is **anchored to a stored `expiresAt` target** (spec §8): every tick — and the `remaining` getter itself — computes `expiresAt.difference(now)`, so a tick delayed by app suspension never under-counts; the countdown jumps straight to the correct value (or expires) on the next fire. The clock is injectable (`now` param, default `DateTime.now`) so tests run on a fake clock. Recommended presets live as `static const presets = <Duration>[15, 30, 45, 60, 90 minutes]` on the service (spec §10). and the timer is based on real elapsed time, never individual songs — a track naturally completing while the countdown runs just advances the queue, leaving the timer active (§15). "Pause behavior" (§6) is satisfied by design — the countdown has nothing to do with playback state, and §9 persistence (surviving force-stop/reboot) is deliberately out of scope. The notification is NOT responsible for the timer (§14, optional in Phase 4A — no OS action wired). State: `isActive` / `remaining` / `expiresAt` getters + `sync: true` broadcast `stateStream` (`Duration?` — null when inactive) + `expiredStream`; `remaining == null` is the single inactive signal (no enum). Providers: `sleepTimerServiceProvider` (`Provider`, `ref.onDispose(service.dispose)` when owned by a container) and `sleepTimerStateProvider` (`StreamProvider<Duration?>` — yields `service.remaining` then `stateStream`, drives the sheet + player AppBar).
- **Wiring:** `PlayerNotifier` subscribes in `_initSubscriptions` (`_sleepTimerExpiredSub` → `unawaited(stop())`, cancelled in `_disposeSubscriptions`) so expiry uses the existing single stop path — no second playback system and no direct player access from the service.
- **UI:** `SleepTimerSheet` (`lib/widgets/player/sleep_timer_sheet.dart`, opened by `showSleepTimerSheet`) — inactive shows the preset menu (Off / 15 / 30 / 45 / 60 / 90 minutes / Custom; Off is the currently-selected state) inside a `SingleChildScrollView` so the modal sheet never overflows; Custom opens a numeric-minutes `AlertDialog` (digits-only input, Start validates > 0, Enter submits, nothing created until Start). Active shows `formatDuration(remaining)` + a "Cancel Timer" button. Entry point: `PlayerScreen`'s AppBar `bedtime_outlined` action → filled `bedtime` (primary color) while active.
- Tests: `test/services/sleep_timer_service_test.dart` (10 — countdown/expiry/cancel/zero-duration/dispose), 7 sheet widget tests, 3 controller tests (expiry stops playback; cancel doesn't; a running timer alone doesn't), 3 `PlayerScreen` AppBar tests. #### Phase 4B — Equalizer & Audio Effects:
- **One player, one session (spec §1):** `main()` **constructs** the single `AudioEffectsService` **before** `AudioService.init` (so its pipeline can be baked into the player) and passes it to `MusicAudioHandler(audioEffects: …)`, which hands `service.audioPipeline` to the **existing** `ja.AudioPlayer` (`ja.AudioPlayer(audioPipeline: …)`) — there is still exactly one `AudioPlayer`, one `MusicAudioHandler` and one `AudioSession`; the EQ/preamp are inserted into the pipeline the notification/lock-screen player already uses, so effects keep applying in the background. `main()` also owns the one `AppDatabase` and overrides `appDatabaseProvider` with it.
- **Startup order, non-blocking (spec §17):** `main()` runs the spec's chain — `AudioService.init` (audio handler up) → `container.read(audioEffectsControllerProvider)` (effects controller up, which unawaited-calls `initialize()`) → settings loaded → supported effects detected → effects applied. `initialize()` is **never awaited on the audio path**; it is guarded step by step (`_guard`: preferences load, `setEqualizerEnabled`, `setPreampDb`, band discovery, native push), so a failing store/backend/platform call leaves the defaults and disables only that one effect while audio plays on. The `ready` future (completes on success *or* failure) exists only for UI code that wants to wait; the player never does.
- **Settings never touch the music database (spec §16):** the effects live in the standalone `audio_effects_settings` singleton row with **no relation** to `tracks`/`albums`/`artists`/`playlists`/`play_history`/`favorites` — writing a band gain, preset or strength never reads or writes a music table, and `MusicRepository.purgeTrackRelations` (spec 23) leaves the row untouched (both are asserted in `test/data/repositories/audio_effects_preferences_test.dart`).
- **Effects outlive the UI (spec §18):** the ownership chain is UI → `AudioEffectsNotifier` → `AudioEffectsService` → `MusicAudioHandler` → the Android audio session, and the session (owned by the audio FGS) is what actually keeps the EQ alive — closing the app UI, popping routes or disposing a `ProviderContainer` cannot stop it. `audioEffectsServiceProvider` therefore only disposes a **detached fallback** instance; the app-wide `globalAudioEffects` is never disposed with a container, so the UI is never what keeps the equalizer alive *or* what kills it.
- **Settings changes never interrupt playback (spec §19):** every mutation only re-sends values to the effect (`setBandGain`/`setPreampGain`/`applyPreset`/native toggle). Nothing reloads the source, seeks, pauses or stops, and the queue, current track and position are untouched; the notification keeps its metadata (`MusicAudioHandler` publishes the media item on source load only, and the effects layer never re-publishes it) — asserted in the controller test via `FakeAudioPlayerService.setFileCount`/`seekCount`/`mediaItemUpdateCount`.
- **Output-device changes (spec §20):** the service exposes `reapplyEffects()` (also on the controller) — it re-sends the current EQ flag, preamp and **every** band gain and re-pushes the native effects, entirely through `_guard`, so it is safe at any time and can never interrupt playback. The player's `androidAudioSessionIdStream` already re-applies the native effects on its own when Android hands over a new session id; `reapplyEffects()` is the explicit hook for the remaining device-change callbacks (headphones, Bluetooth, USB DAC).
- **One audio session, never a second (spec §21):** the app's single `AudioSession` is configured in exactly one place — `MusicAudioHandler._configureSession` (`lib/player/audio_handler.dart`) — and the effects layer never touches it: the screens and `AudioEffectsNotifier` reach the *existing* player/session through `AudioEffectsService`, whose only session input is the id just_audio reports on `androidAudioSessionIdStream` (the native effects attach to that very id). `test/services/audio_session_architecture_test.dart` enforces this at the source level: exactly one file configures a session, no file under `controllers/audio_effects_controller.dart`, `screens/player/equalizer_screen.dart`, `screens/player/audio_effects_screen.dart` or `services/audio_effects/` mentions `AudioSession` or constructs a player, and `audio_handler.dart` still creates exactly one `AudioPlayer`.
- **Failures disable an effect, never playback (spec §22):** **every** engine call goes through `_guard(step, onFailure: …)`, so nothing can throw into the audio path or into a slider callback: a failed equalizer/band update flips `supported: false` (the UI then says "The equalizer is not available on this device." and disables its switch), a failed **preamp** call flips only `preampAvailable: false` via `_markPreampUnavailable` (its own effect, its own failure — it must never take the band sliders and presets down with it), a failed native push flips `bassBoostAvailable`/`virtualizerAvailable` false, and the rest of the chain carries on. The settings are kept, so a device that recovers can be re-enabled. `AudioEffectsState` holds **no** error/message string, so no Android exception text can ever reach the normal UI (asserted: a `PlatformException` carrying `java.lang.RuntimeException: audiofx blew up` leaves no trace in the snapshot).
- **A slider is a single band update (spec §23):** moving a band slider re-sends that one band gain and nothing else — it never re-initialises the player, reloads the source, seeks or re-queues. The widget test asserts it through `FakeAudioPlayerService` (`setFileCount`/`loadedPath`/`playCount` stay 0) and through the backend call list, which contains only `setBandGain(0, …)`.
- **Rapid slider updates are coalesced (spec §24):** the state (and therefore the slider) follows the finger **immediately**, while the platform is told at most once per `bandUpdateThrottle` (60 ms, `AudioEffectsService.defaultBandUpdateThrottle`) per band — leading edge sent right away so a single tap applies immediately, the rest of the burst merged into one trailing update with the **latest** value. Because the push is what persists, this also collapses a drag's per-pixel database writes into one per window. The window is cancellable in effect (`_supersedePendingBandGains`, so a preset/reset is never overwritten by a stale slider value), `flushBandGains()` (also on the controller) forces a pending value out, and `dispose()` flushes before releasing so a drag that ended moments earlier is not lost. The scheduler is injectable (`delay:`) for tests; **widget tests must inject a synchronous delay** (or fire the collected windows themselves) because `flutter_test` fails a test that ends with the 60 ms window still pending.
- **Native pushes are serialized, newest value wins (spec §24, native side):** every preamp/native mutation is fire-and-forget from a slider, so a drag used to leave a dozen `apply` calls crossing the `MethodChannel` at once. They complete out of order, and `MainActivity` applies `setTargetGain`/`setStrength` in *completion* order — so the gain the effect ended up with was whichever value happened to land last, in practice an early one. Because Android documents `0 mB` as "no amplification", that is a **silent** bug: the slider showed a large boost while the effect sat at no boost at all. `_pushNativeEffects` is therefore a single-flight drain (`_nativePushDrain` + `_nativePushQueued`): a push arriving while one is in flight marks the run dirty and lets it loop once more with the newest state instead of racing it, and a queued caller awaits that drain. The last push issued therefore always carries the current values. `_pushNativeEffectsOnce` is the single round trip.
- **A fresh preamp engage starts audible:** `setPreampEnabled(true)` from nothing snaps a still-`0 dB` gain up to `AudioEffectsService.defaultPreampDb` (+6 dB) and persists it, because 0 dB is a documented no-op for `LoudnessEnhancer` and the switch otherwise did nothing until the slider was dragged. A gain the user chose — or one restored from the preferences — is never overwritten, so it only fires on a genuine off→on transition.
- **`AudioEffectsService`** (`lib/services/audio_effects/audio_effects_service.dart`) owns **all** audio-processing state and is the only place that talks to the audio engine. Public surface: `audioPipeline` (the pipeline to bake into the single player), `initialize()` (idempotent: restore → apply EQ/preamp → query bands → push native effects) + `ready`, `stateStream`/`state`, `isSupported`, `bassBoostSupported`, `virtualizerSupported`, `bindSessionIdStream(Stream<int?>)`, `setEqualizerEnabled`, `setBandGain(index, gain)` (clamped to the backend range; **clears `presetId` → custom**), `setPreampEnabled` (fresh engage starts at `defaultPreampDb`)/`setPreampGain` (own 0…+20 dB range), `setBassBoostEnabled`/`setBassBoost` (0–1), `setVirtualizerEnabled`/`setVirtualizer` (0–1), `applyPreset(EqPreset)`/`applyPresetById` (resampled onto the real band count), `reset()`, `reapplyEffects()` (spec §20), `flushBandGains()` (spec §24), `bandUpdateThrottle`/`defaultBandUpdateThrottle` (60 ms coalescing window), `defaultPreampDb`, `dispose()`. Held in the `globalAudioEffects` global (like `globalAudioHandler`) and exposed via `audioEffectsServiceProvider` (falls back to a detached instance in tests) + `audioEffectsStateProvider` (`StreamProvider`).
- **Dynamic bands (spec §5):** nothing about the band layout is hard-coded. `AudioEffectsBackend.bands` (a `Future`) is mapped into `EqBandsConfig{bands, minDecibels, maxDecibels}`, so a device with 3/5/10 bands renders correctly; Android only answers after the first source is loaded, so the state carries a three-way signal: `resolved` (the backend answered), `supported` (answered: yes/no) and `parametersReady` (bands present). A stored curve is **resampled** onto whatever band count comes back, so settings survive a device/ROM change.
- **EQ backend (equalizer only — the preamp is NOT here):** `JustAudioEffectsBackend` (`audio_effects_backend.dart`) wraps just_audio's own `AudioPipeline` with `AndroidEqualizer`, and nothing else. just_audio re-applies gains/flags on every source load, so the EQ survives track changes and background playback. **The effect must be explicitly `setEnabled` — just_audio seeds `enabled` to `false` and `AudioPlayer.java` only calls `setEnabled(true)` when the serialized message says so, so an equalizer that is created but never enabled is permanently bypassed** (every parameter write succeeds and no sound ever comes out). Off Android (and off `dart:io`-unsafe targets) it reports unsupported; the UI then shows "not available on this device".
- **Native preamp + bass boost + virtualizer:** just_audio's pipeline has no `LoudnessEnhancer`/`BassBoost`/`Virtualizer`, so `NativeEffectsBridge` (`native_effects_bridge.dart`) talks to `MainActivity` over the `com.example.test_app/audio_effects` `MethodChannel` (`applyEffects`/`releaseEffects`) and drives **all three** there. The preamp in particular must *not* ride just_audio's `AndroidLoudnessEnhancer`: that path no-ops silently in three ways — writes landing before the effect is attached to a live session are discarded, just_audio drops parameter writes made before the effect has a session, and the effect is rebuilt from a platform-init snapshot on every session change so a later gain reverts. Driven natively it is created for the session that is actually playing, the target gain is written **before** `setEnabled(true)`, and it is rebuilt on every session change. The effects are attached to the **same** audio session id just_audio reports (`_player.androidAudioSessionIdStream` → `service.bindSessionIdStream`), and are **re-created whenever that id changes** (an `AudioEffect` is bound to its session); a `null` id releases them. Availability comes back from the platform and lives in the `AudioEffectsState` snapshot (`preampAvailable`/`bassBoostAvailable`/`virtualizerAvailable` + `nativeResolved` for "not asked yet") — deliberately *not* separate service fields, so the UI actually rebuilds when the session makes the effects usable. `NoopNativeEffectsBridge` is the non-Android/test implementation; no caller null-checks.
- **Strength is device-driven, never assumed (spec §12/§13):** strengths stay normalized 0.0–1.0 in the state, the controller and the persisted preferences; `MainActivity` maps them onto the scale its effect accepts (`scaleStrength` → the deprecated `short` per-mille `setStrength`) and reports the scale back, so Dart never hard-codes a per-device integer range. Android exposes **no** public strength-range query for these two effects — the only real capability signal is `BassBoost/Virtualizer.getStrengthSupported()`, which is queried at effect creation and surfaces as `bassBoostStrengthSupported`/`virtualizerStrengthSupported` in the snapshot. A device that refuses strength changes keeps the effect switchable but shows no slider; a device that has no effect at all shows "`<Effect> unavailable on this device.`" with the switch disabled. Every native call is wrapped in try/catch and a failure releases the effect instead of throwing, so playback is never affected (spec §12/§13). `StrengthRange` (in `lib/models/audio_effects.dart`) is the generic reported-scale value type; `StrengthRange.full` (0–1000) is the platform's documented per-mille contract and `isDefault` hides the device-range hint when it applies.
- **Persistence (spec §15):** the `audio_effects_settings` singleton table (schema v10) + `AudioEffectsPreferences` (`lib/data/repositories/audio_effects_preferences.dart`, `load`/`save`/`clear`, `PersistedAudioEffectsSettings`, band gains as a JSON string). These are app preferences, not library data: a single lightweight row with **no relation to tracks**, `audioEffectsPreferencesProvider` backed by `appDatabaseProvider`, and the service's ctor param is `preferences`. Every mutation persists; `AudioEffectsState` stays the single in-memory source of truth.
- **Gain range (spec §6):** the sliders are mapped to the range the backend actually reports — `EqBandsConfig.minDecibels`/`maxDecibels` come from `AndroidEqualizerParameters` and flow into `AudioEffectsState`; nothing in the UI or the service assumes ±12 dB (`_clampGain` and `EqPreset.sampleFor` clamp to the reported range, and a curve stored on a ±15 dB device is re-clamped on a ±10 dB one). **The preamp has its own range, never the bands'**: Android's `LoudnessEnhancer` documents `0 mB` as "no amplification" (it only ever boosts, and compresses rather than attenuates out-of-range peaks), so the backend reports `preampMinDb` = 0 and `preampMaxDb` = +20 dB (the platform's 2000 mB cap — there is no public range query, so this is the documented contract, mirroring how `StrengthRange` works) and `_clampPreamp` clamps to it. Mapped onto the bands' symmetric ±12 dB the preamp asked the platform for something it does not do.
- **Presets (spec §7/§8):** `eqPresets` is the full 13-entry list (Normal, Acoustic, Bass Booster, Bass Reducer, Classical, Dance, Deep, Electronic, Hip-Hop, Jazz, Pop, Rock, Vocal) and each `EqPreset` is **just a curve of gain values** (no preamp, no enabled flag), mapped onto the real band count by `sampleFor`. A preset is only offered when it genuinely fits the device: `EqPreset.appliesTo(bandCount)` is `bandCount >= gains.length` and `eqPresetsFor(bandCount)` filters the row, so the 5-point built-in curves are offered on 5- and 10-band devices while a 3-band equalizer says "No presets fit this device's 3 equalizer bands" instead of silently dropping curve points. Restoring/applying a preset never writes the preamp — only band gains and the active `presetId`.
- **Custom (spec §9) + reset (spec §10):** hand-editing any band clears `presetId`, and the chip row then shows a non-selectable `Custom` chip. `reset()` restores flat gains + the **Normal** preset + a zeroed preamp and switches bass boost/virtualizer off (leaving the equalizer's own engage switch alone, since the spec's list doesn't include it); it touches only audio processing — volume, queue, playback position, favorites, playlists and history live outside `AudioEffectsService` and are asserted untouched in the controller test.
- **Bypass keeps settings (spec §11):** the equalizer's master switch only engages/bypasses the effect — the preset, the band gains and the preamp are never cleared or rewritten, so switching it back on restores the curve exactly as it was (covered by a screen test that bypasses and re-engages). The **preamp has its own engage switch** (`setPreampEnabled`, persisted as `audio_effects_settings.preamp_enabled`): it can be raised with the bands bypassed, bypassing it keeps its stored gain, and it is never gated on `equalizerEnabled`.
- **UI:** `AudioEffectsScreen` (`lib/screens/player/audio_effects_screen.dart`) is the audio-effects **hub** (spec §14) and the only effects screen the Options menu needs to open: the equalizer row (master switch + an "Edit bands and preset" button into `EqualizerScreen`) followed by Bass Boost / Virtualizer with their own switch and 0–100 % strength slider, each with 0 %/100 % end labels, the platform's reported strength scale when it isn't the default one, and the explanatory `_Note` copy for an unavailable effect or a non-adjustable strength. An AppBar `restart_alt` (tooltip "Reset audio effects") resets everything. `EqualizerScreen` (`lib/screens/player/equalizer_screen.dart`) now owns **only** the equalizer — the master switch (+ "not available" / "band information appears once the first track starts playing" states), the horizontally scrolling `ChoiceChip` preset row (one row instead of a 4-row wrap, so the band sliders stay on screen with all 13 presets) that shows a non-selectable `Custom` chip once a band is hand-edited, a dB scale plus one vertical (`RotatedBox`) slider per backend-reported band, and the Preamp. Entry points: `PlayerScreen`'s **Options** menu offers **Audio Effects** (→ the hub) and **Equalizer** (→ the band screen) as live rows, with Lyrics / Playback Speed still disabled placeholders.

### 5. `player/`
The playback engine — the single most important architectural island in the app.

```
player/
├── player_controller.dart     # PlayerNotifier: playback lifecycle, queue, repeat & shuffle
├── player_state.dart          # Immutable PlayerState snapshot + RepeatMode/PlayerProcessingState enums
└── queue/                     # Phase 3E spec queue (wired into PlayerNotifier)
    ├── queue_item.dart        # QueueItem: track + session-unique id
    └── playback_queue.dart    # Unmodifiable-items queue (setQueue/add/next/previous)
```

- **Single AudioPlayer Rule:** There is exactly one `AudioPlayer` instance for the entire application, owned by the app-wide `MusicAudioHandler` and exposed through the singleton `audioPlayerServiceProvider`. No screen or widget constructs its own player.
- **Phase 3H — Playback history, resume, and play count:** `PlaybackHistoryService` is now Drift-backed (see `services/playback/`); it dedups by track id (replay moves the entry to the top, most-recent-first = the spec's `ORDER BY last_played_at DESC`, 3H.10), records `playCount`, `lastPlayedAt`, and per-track `resumePositionMs`. `PlayerController` wires it in: `play()` no longer records immediately (3H.6 — a tap that fails before ready must not count); instead `_handlePosition` (fed by the position stream) records a play only once the track has been listened to past `_playCountThreshold` (10s, 3H.8/3H.9), guarded by the per-track `_playRecordedForCurrentTrack` flag that `_loadTrack` resets on each new track so pause/resume and repeated rebuilds never re-count. Resume persists run through the throttled `_saveResumePosition` (3H.15 — a `_lastResumeSave` timestamp gates writes to at most one per 5s session window; also re-anchored by an active `seek` past the threshold, 3H.14). It fires from `_persistResumeForCurrent` (3H.16), which first normalizes the position via `_resumeValueFor`: a non-meaningful point — near the start (`<= _resumeThreshold`) or near the end (`>= duration - _resumeEdge`, matching 3H.18) — is written as `Duration.zero` (clearing any stale resume) instead of merely being skipped, and clearing writes bypass the 5s throttle so a stale point is always dropped. These persist calls come from `pause()`, and `stop()` (the old `_loadTrack` pre-load flush would see only the incoming track at position 0, so it was removed); natural completion saves `Duration.zero` directly (3H.17) so a finished song never resumes from its end. Reopening a track calls `_maybeResume` (past 5s and before `duration − 5s` per 3H.18 — `_resumeThreshold`/`_resumeEdge`) to `seek()` and sets `PlayerState.resumedFrom` (cleared via `dismissResume()` and at natural completion). The resume seek is controller-only (3H.20 — one source of truth; the audio handler never seeks independently). `PlayerState.resumedFrom`/`copyWith.clearResumedFrom` expose the indication to `PlayerScreen`'s dismissible `_ResumeBanner`.
- **Phase 3G — Background playback (audio_service):** The player now bridges to the OS via `audio_service`. `lib/player/audio_handler.dart` (`MusicAudioHandler extends BaseAudioHandler with SeekHandler`) owns the single `ja.AudioPlayer` and publishes a media session: `playbackState` (controls, `updatePosition`, `processingState`, `systemActions`) broadcast from `playbackEventStream`, plus `mediaItem` metadata (title/artist/album/duration/artUri) from `Track`. `main()` calls `AudioService.init(builder: MusicAudioHandler.new, config: ...)` *before* `runApp` and stores the result in the global `globalAudioHandler`; the controller's `audioPlayerServiceProvider` wraps that handler in `AudioPlayerService` (falling back to a fresh `MusicAudioHandler` when the global is unset, e.g. widget/unit tests). **`AudioPlayerService` keeps its exact public surface** (position/duration/playerState/processingState/completed streams; `setAsset`/`setFile`/`play`/`pause`/`stop`/`seek`) so the controller and `FakeAudioPlayerService` are unchanged — it now *delegates* to `MusicAudioHandler` instead of owning a player. New facade methods: `setOsHandlers({onNext, onPrevious})` (routes notification/lock-screen/headset navigation back into the controller's shuffle/repeat-aware `next()`/`previous()`, then `refreshOsPlaybackState()`), and `updateOsMediaItem(Track)`. Android wiring: manifest adds `WAKE_LOCK`/`FOREGROUND_SERVICE`/`FOREGROUND_SERVICE_MEDIA_PLAYBACK` permissions, the `com.ryanheise.audioservice.AudioService` (foregroundServiceType `mediaPlayback`, MediaBrowserService intent), and `com.ryanheise.audioservice.MediaButtonReceiver`; `MainActivity` now extends `AudioServiceActivity` (shared Flutter engine so notification tap resumes the app). `AudioSession` is configured for music on a guarded async path so headless/test environments stay inert — 3G.20/3G.21 add an `interruptionEventStream` listener (pause on interruption begin) and a `becomingNoisyEventStream` listener (pause on headphone disconnect). Debug APK builds clean.

- **Phase 3F — PlaybackMode layer (part 2, navigation wired):** `lib/player/playback_mode.dart` owns `RepeatMode` + immutable `PlaybackMode{shuffleEnabled, repeatMode}` — the playback-navigation layer kept out of `PlaybackQueue` (3F.3). `PlayerNotifier` holds `_playbackMode` (exposed as `PlaybackMode get playbackMode`, 3F.7) and mirrors it into `PlayerState.shuffleEnabled`/`repeatMode` via `_applyPlaybackMode` (spec's `notifyListeners()`). `toggleShuffle` (3F.7) builds/clears the id-based `_shuffleOrder` + `_shufflePosition` (`_createShuffleOrder()`, 3F.5, pins current item first per 3F.6) — the visible queue is never reordered (3F.1). `cycleRepeatMode` cycles OFF→ALL→ONE (3F.8). **Navigation** is now spec's: `next()` (3F.15) and completion (`_handleTrackCompleted`, 3F.10) share `_getNextPlaybackItem()` (3F.11: shuffle-aware; sequential `items[currentIndex+1]`; repeat-all wraps to index 0). `_getNextShuffleItem()` (3F.12) walks `_shuffleOrder` by id via `_findQueueItem()`, and Repeat ALL regenerates a fresh order each cycle (3F.13) starting at position 1 — the current item, pinned at 0, is never played twice in a row (3F.14). Repeat ONE restarts via `seek(0)`+`play()` (3F.9). `previous()` (3F.16) keeps the `>3s` restart boundary, then `_getPreviousPlaybackItem()`: shuffle-aware `_getPreviousShuffleItem()` (provisional symmetric walk), sequential `items[currentIndex-1]`, and repeat-all wraps to the last item. `_shufflePosition` is now consumed (analyze clean). Queue-mutation safety (3F.18): `_refreshShuffleState()` prunes stale ids from `_shuffleOrder` after every `playNext`/`addToQueue`/`removeFromQueue`/`moveInQueue`/`clearQueue`; reordering is harmless since ids are position-independent (3F.19). `PlayerScreen`'s shuffle/repeat row now sits above the transport controls (3F.20). STILL PENDING: `setQueue`'s shuffle path still reshuffles the visible queue via the old `_shuffledOrder` pin — the 3F `setQueue` section will move that into `_shuffleOrder` too.
- **Playback State:** `PlayerNotifier` (Riverpod `Notifier<PlayerState>`) coordinates Playback (play/pause), Position, Duration, buffering/loading, and emits an immutable `PlayerState` snapshot for the UI. The backing queue is exposed as `PlaybackQueue get queue` (3E.10). Public surface: `playQueueItem` (3E.11 — resolves a `QueueItem` by id to an index, then plays), `playTrack`, `playQueue` (queue-context playback at an index), `setQueue` (optional autoPlay + shuffle), `play`/`pause`/`togglePlayPause`, `stop`, `seek`, `next`/`previous` (3F.15/3F.16 — share the completion navigation rules via `_getNextPlaybackItem`/`_getPreviousPlaybackItem`; `previous` restarts only when `position > 3s`, else goes to the previous item, seeking to zero at the queue start; repeat-all wraps at the boundaries), `jumpToIndex`, `playNext`/`addToQueue`/`removeFromQueue`, `playNextAll(List<Track>)`/`addToQueueAll(List<Track>)` (3K.4/3K.5 — queue-only batch inserts, reverse-`addNext` preserves order for Play Next, shuffle state refreshed), `moveInQueue` (reorder by index, clamps; relays to `PlaybackQueue.move`), `clearQueue`, `toggleShuffle`, `cycleRepeatMode`, `clearError`. Playback failures route through `_setError` → `processingState = error` + dismissible `error` message; `isPlaying` mirrors the engine — driven by `playerStateStream` *and* reconciled against `_audioService.playing` by `play()`/`pause()` after each successful call, because just_audio's `play()`/`pause()` are silent no-ops when already in the requested state and loading a new source over a playing engine keeps playing (a swapped source must never leave the button showing "play" while audio runs). `play()` on a parked `completed` state (end-of-queue, repeat off) seeks to zero first (mirroring Repeat ONE) so the finished track replays instead of doing nothing.
- **Phase 3E — Spec Queue Model:** The playback queue is the spec's `lib/player/queue/playback_queue.dart`: a single `_items` list of `QueueItem(id, track)` (session-unique ids via `DateTime.now().microsecondsSinceEpoch` + `Random`; same track may appear twice). `items` is exposed only as `List.unmodifiable(_items)` (3E.4 — all mutation goes through the class, so `items.clear()` is rejected). Ops: `setQueue(tracks, {initialIndex})` (clamps), `next`/`previous` (roll one, null at bounds), `setCurrentIndex`, `clear`, `add(Track)` (3E.5, append, leaves index alone), `addNext(Track)` (3E.6, insert after `_currentIndex`), `removeAt(index)` (3E.7, keeps `_currentIndex` on the same playing item: shifts down when removing before it, falls onto the next when removing it, snaps to the new tail when removing the current last item, resets when emptied), `move(oldIndex, newIndex)` (3E.8, bounds-checked; keeps `_currentIndex` pinned to the playing item whether moved directly or merely crossed). **Queue separation (3E.9):** `add`/`addNext`/`removeAt`/`move` only modify the queue; playback always starts through `playTrack`/`playQueueItem`. `PlayerNotifier` owns the spec queue (`final PlaybackQueue _queue`) and emits `PlayerState.queue` as plain `List<Track>` via `_syncQueueState`. `setQueue` pins the target track first via `_shuffledOrder` when shuffle is enabled (interim shuffle handling until the Phase 3F `setQueue` section). The `QueueScreen` splits the queue into a pinned `Playing` section and a reorderable `Up Next` section (drag handles via `ReorderableListView` + `onReorderItem`) with a bottom `Clear Queue` button. Up-next rows resolve their `QueueItem` from the controller's `queue.items` and jump via `playQueueItem(queueItem)` (3E.18); each row carries a trailing `PopupMenuButton` with `Remove from queue` → `removeFromQueue(queueIndex)` (3E.19; Play next / Add to playlist deferred). Unit-tested in `test/player/queue/playback_queue_test.dart`; controller integration tested in `test/controllers/player_controller_test.dart`; QueueScreen widget-tested in `test/screens/queue_screen_test.dart`.
- **Phase 3B — Processing State Machine:** `PlayerState.processingState` (`PlayerProcessingState`) is the single source of truth for the engine lifecycle: `idle` → `loading` (source prepared) → `ready` / `buffering` / `completed` / `error`. `AudioPlayerService` maps just_audio's low-level states onto `PlayerProcessingState` (`processingStateStream`); the controller subscribes to `playerStateStream` (isPlaying) and `processingStateStream`, and `isLoading`/`isBuffering`/`isCompleted` are derived getters, so UI flags cannot drift from the engine. Natural track completion advances the queue; the last track leaves the state `completed` with `position` pinned at `duration` (no pause/seek needed — the source already ended).
- **Phase 4A — Sleep Timer wiring:** `PlayerNotifier` subscribes to the shared `SleepTimerService.expiredStream` in `_initSubscriptions` (`_sleepTimerExpiredSub` → `unawaited(stop())`, cancelled in `_disposeSubscriptions`) so expiry uses the only existing stop path — no second playback system and no direct player access from the service. `cancel()` never touches playback/history/queue/playlists. Track completion never cancels the timer — a finished song advances the queue normally while the countdown runs on real elapsed time (spec §15).
- **Phase 4B — Effects injected into the one player:** `MusicAudioHandler` takes an optional `AudioEffectsService` and builds the single player as `ja.AudioPlayer(audioPipeline: audioEffects?.audioPipeline)`, then feeds `_player.androidAudioSessionIdStream` into `service.bindSessionIdStream(...)`. Nothing else in `player/` changed — the queue, history, resume and shuffle rules are untouched, and no second player/handler/session exists.
- **Phase 4A — Sleep Timer UI (specs §12/§13):** `PlayerScreen`'s AppBar action is a compact indicator while active — a `FilledButton.tonalIcon` pill with `Icons.bedtime` + `formatDuration(remaining)` (e.g. `29:42`), swapping to the plain `bedtime_outlined` `IconButton` when inactive; both open the sleep timer sheet. An `Options` `TextButton.icon` (`Icons.more_horiz`) below the transport controls opens the **player options menu** (spec §13, `_showPlayerOptions`) — a modal bottom sheet with a 'Player' header and Queue (→ `QueueScreen`) + Sleep Timer (→ sheet) live, and Equalizer / Audio Effects / Lyrics / Playback Speed as disabled placeholders (no-op `onTap: null`); the sheet content is wrapped in a `SingleChildScrollView` so it never overflows its modal constraints. The old standalone 'Queue' button was replaced by the menu.
- **UI Connectivity:** All playback UI (MiniPlayer, full `PlayerScreen`, `QueueScreen`, `TrackTile` actions, shuffle buttons) reads/writes through `playerNotifierProvider` only. Play/pause buttons never key off `isPlaying` alone (Phase 3B.16): while `isBuffering` they render a spinner instead of a play icon, and `PlayerScreen` shows an error banner when `hasError`. While `isLoading` the entire `PlaybackControls` row is disabled and its center button shows a spinner (Phase 3D.4; supersedes the old artwork overlay).
